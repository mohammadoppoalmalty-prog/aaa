## HOW TO READ THIS DOCUMENT

This charter takes the nine categories of engineering and UX standards supplied for this project and resolves each individual item into a **decision**, not an aspiration. Nothing is listed as "we should consider."

Every row carries a verdict:

| Verdict | Meaning |
|---|---|
| ✅ **Adopted** | Applies directly. The implementation is named. |
| 🔄 **Web equivalent** | The item is a React Native / mobile-native concept. The equivalent web technique is named and adopted. |
| ⚠️ **Scoped** | Adopted, but deliberately narrowed. The boundary is stated. |
| ❌ **Rejected** | Not used. The reason is stated. Rejections are decisions, not oversights. |

**A structural note that governs everything below.** This project has two layers ([GDD Part 0](GDD.md#part-0--the-one-structural-decision)):

- **Layer 1 — The World**: a WebGL scene. It has no DOM, no scroll, no lists. Standards about virtualization, re-render optimization, and memory leaks apply here *ferociously*, in their 3D form.
- **Layer 2 — The Codex**: a conventional server-rendered site. Every classic web-UI standard applies here in its normal form.

Many items below split across both layers, and the split is stated each time. Confusing the two is the fastest way to apply a good rule in the wrong place.

## 1 · LISTS, LOADING & DATA FETCHING

### Where lists actually exist in this project

Before deciding anything, the honest inventory — because most of this project has **no lists at all**, and pretending otherwise would produce ceremony instead of engineering.

| Surface | Item count | Growth | Verdict |
|---|---:|---|---|
| **Tree of Visitors** (leaf list view) | 0 → unbounded | Grows forever | **The only true list in the project.** Everything in this section is designed for it. |
| Diary feed (`/codex/diary`) | 10 → ~200 | Slow, developer-authored | Paginated, static |
| Codex memory grid | Fixed 100 | Never | No pagination. A fixed grid. |
| Projects grid | Fixed 10 | Rare | No pagination |
| Guardian conversation | ≤ 20 per session | Bounded by rate limit | No virtualization needed |
| Achievements / skills / certificates | Fixed, < 30 | Never | Plain render |
| **The 3D world** | ~40,000 instances | Fixed per area | Instancing + culling, not list virtualization |

**The rule that follows:** heavy list machinery is built **once**, for the Tree, and is not applied to fixed-size collections where it would add complexity, JS weight, and CLS risk for zero gain.

### Decisions

| # | Standard | Verdict | Implementation in this project |
|---|---|---|---|
| 1.1 | **Pagination** | ✅ Adopted | `GET /api/leaves` returns pages of 40. `/codex/diary` paginates at 20 per page with real `<a href>` links (crawlable, unlike infinite scroll). The Codex's fixed collections are unpaginated by design. |
| 1.2 | **Cursor-based vs offset-based** | ✅ Adopted — **cursor, mandatory** | This is the single most important row in section 1. New leaves arrive *while a visitor is scrolling*, so an offset (`LIMIT 40 OFFSET 80`) would silently duplicate or skip leaves as rows shift. The cursor is a compound key: `(created_at, id)` base64-encoded, with `WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 41` — fetching 41 to detect `hasMore` without a second `COUNT(*)`. `id` is the tiebreaker because two leaves can share a timestamp. Offset pagination is **banned** in this codebase and the ban is enforced by a lint rule on the Drizzle query layer. |
| 1.3 | **FlashList** | 🔄 Web equivalent | FlashList is a React Native library and cannot be used here. Its actual technique — recycling a small pool of views instead of mounting one per row — has two web equivalents, and this project uses both, in different layers: **(a) Layer 2**: `@tanstack/react-virtual` on the Tree's list view, activating only past 200 leaves (below that, plain rendering is faster and avoids the scroll-anchoring bugs virtualization introduces). **(b) Layer 1**: `THREE.InstancedMesh` *is* view recycling, executed on the GPU — one draw call renders 2,000 leaves on the Tree, 40,000 foliage instances in the Forest, and 12 village spirits. The Tree's 3D form and its list form are the same data through two different recyclers. |
| 1.4 | **Skeleton Loading** | ⚠️ Scoped | Most of the Codex is statically generated — its content arrives *with the HTML*, so a skeleton there would be pure theatre, showing a grey box before instantly-available text. Skeletons are used in exactly four places: the Tree's leaf list (server data), the diary's paginated pages, the project demo `<iframe>` (third-party, genuinely slow), and the Guardian's reply bubble while the first token is in flight. **Layer 1's skeleton is the loading ring rendered as the gate's glyphs igniting** — same principle, in-fiction. |
| 1.5 | **Shimmer Effect** | ⚠️ Scoped | Applied to the four skeletons above, as a CSS `background-position` animation on a `linear-gradient` — **animating `background-position`, not `left`**, so it stays off the main thread. **Hard requirement: `@media (prefers-reduced-motion: reduce)` replaces the shimmer with a static 8%-opacity fill.** A pulsing gradient is a vestibular trigger, and this project claims full Reduced Motion support. |
| 1.6 | **Skeleton Dynamic Layouts** | ✅ Adopted | Leaf messages vary from 8 to 180 characters, so a fixed-height skeleton guarantees a layout shift when real text lands. The skeleton renders **three width variants** (short/medium/long) cycled deterministically by index, sized from the measured p50 leaf length in production, and the container reserves the p90 height. Combined with row-level `content-visibility: auto`, this holds CLS at 0. |
| 1.7 | **Infinite Scroll** | ⚠️ Scoped — **Tree only** | Infinite scroll is adopted for the Tree's list view (browsing thousands of stranger messages is a lean-back activity where a page control would be friction) and **rejected everywhere else in the Codex**. On a portfolio, infinite scroll destroys the two things that matter most: the ability to reach the footer (contact links) and crawlable pagination for search engines. Implementation: `IntersectionObserver` on a sentinel 600 px before the end, with a **manual "Load more" fallback button always present** below it — so keyboard and screen-reader users are never trapped in a list that only advances on scroll, which is a WCAG failure that most infinite-scroll implementations ship with. |
| 1.8 | **Lazy Loading** | ✅ Adopted | Four layers. **(a)** The entire world engine is a `next/dynamic` import with `ssr: false` — the title screen never downloads Three.js. **(b)** Per-area chunk streaming ([GDD Part 11](GDD.md#asset-streaming)). **(c)** Project code panels, architecture SVGs, and demo iframes load on first open, never on area load. **(d)** `loading="lazy"` + `decoding="async"` on every below-fold Codex image. |
| 1.9 | **Pre-fetching / Pre-loading** | ✅ Adopted | The world's **Warm tier** *is* prefetching — adjacent areas load at LOD1 while the player is still in the current one, which is why area transitions have no loading screen. Additionally: `<link rel="preload">` for the two critical fonts and the title-screen image; Next.js `<Link prefetch>` on Codex navigation; the Forest chunk preloads *during* the Gate cinematic so the tutorial area is never waited on; and the next leaf page prefetches at 80% scroll depth. **Guard:** prefetching is suppressed when `navigator.connection.saveData` is true or `effectiveType` is `2g`/`slow-2g` — prefetching on a metered connection is spending someone else's money. |
| 1.10 | **Stale-While-Revalidate (SWR)** | ✅ Adopted | Applied to the Tree list and the diary via both HTTP (`Cache-Control: public, s-maxage=60, stale-while-revalidate=600` at the edge) and the client (TanStack Query with `staleTime: 60_000`). **Explicitly NOT applied to the save file** — the local save is the single source of truth for progress, and there is no server copy to revalidate against. Applying SWR semantics to game state would be a category error that could silently roll back a player's progress. |

### The one thing section 1 must not break

Every technique above is a *loading* optimization, and this project's hardest constraint is **time to portfolio content ≤ 1 input** ([GDD Part 1](GDD.md#hard-constraints)). Therefore:

> **No skeleton, spinner, shimmer, or lazy boundary may ever sit between a visitor and the Codex.** `/codex` and all its sub-routes are fully static, pre-rendered at build time, and ship their content in the first HTML response. If a change ever introduces a loading state on a Codex content route, the build fails a Playwright assertion that checks for the presence of real text in the initial HTML response with JavaScript disabled.

## 2 · INTERACTIONS & UX FEEDBACK

| # | Standard | Verdict | Implementation in this project |
|---|---|---|---|
| 2.1 | **Optimistic UI** | ✅ Adopted | Three places. **(a) Leaf planting** — already specified in [GDD 5.8](GDD.md#58--the-legacy-system--the-tree-of-visitors): the leaf grows on the Tree instantly, before moderation, visible to its author. **(b) Contact form** — the send animation and the Guardian's response fire immediately; a failure surfaces as a retry card that preserves the typed message (never a lost draft). **(c) Everything in the world is optimistic by nature** — memory recovery, puzzle state, and achievements are all local-first with no server round trip, which is why the world feels instant and why the save architecture is local-first. **Reconciliation rule:** an optimistic action that later fails must never silently disappear. It degrades to a visible, actionable state with the user's data intact. |
| 2.2 | **Micro-interactions** | ✅ Adopted | The project's interaction vocabulary, specified so it stays consistent: memory recovery (time dilation + particle burst + card, 4.2 s, [GDD 5.1](GDD.md#51--the-memory-system)); puzzle piece snap (150 ms spring + click + 2 px overshoot); rejection (120 ms shake, 6 px amplitude, low chime — never red-flash, which reads as an error rather than a wrong guess); LUMA acknowledgement (fragment orbit accelerates 40% for 400 ms before it speaks); button press (2 px translate + 60 ms); achievement toast (slide + settle, 350 ms). **Rule:** every micro-interaction is ≤ 400 ms and is driven by `transform`/`opacity` only. |
| 2.3 | **Haptic Feedback** | 🔄 Web equivalent, ⚠️ scoped | The RN Haptics API does not exist on the web. Two real equivalents are used: **(a) `navigator.vibrate()`** — supported on Android Chrome/Firefox, **not supported on iOS Safari at all**, which is stated here so nobody debugs it for an afternoon. Patterns: memory recovered `[18]`, puzzle solved `[14, 40, 14]`, rejection `[30]`. **(b) `GamepadHapticActuator.playEffect()`** for controller users — a genuinely good fit for the Sky Bridge assembly cascades. Both are **off by default** and enabled by a settings toggle; unrequested vibration is hostile, and on some devices it is a seizure and anxiety trigger. `navigator.vibrate` calls are wrapped in a feature check that no-ops silently rather than throwing. |
| 2.4 | **Pull-to-Refresh** | ⚠️ Scoped — **Codex only, and actively blocked in the world** | Adopted on mobile web for `/codex/tree` and `/codex/diary`, the only two surfaces with server data worth refreshing. It is **deliberately blocked on the world canvas** via `overscroll-behavior: none` plus `touch-action: none` — because on the world, a downward drag is the look control, and a browser-native pull-to-refresh firing mid-puzzle would reload the page and feel like a crash. Blocking the browser gesture here is a correctness requirement, not a preference. |
| 2.5 | **Action Sheets & Bottom Sheets** | ✅ Adopted | Mobile-only. Three sheets: the **Codex sheet** (swipe-up from the persistent bottom button, three detents at 45%/85%/full), the **Settings sheet**, and the **LUMA conversation sheet**. All built on the native `<dialog>` element with `showModal()` so focus trapping, `Esc`, and the top layer come from the platform rather than from 300 lines of hand-rolled focus management. Anchored to the bottom because that is the thumb zone — see [Fitts's Law, 6.6](#6--ux-research--behavioral-cognition). Drag-to-dismiss with a velocity threshold, plus a visible close control for anyone who cannot drag. |
| 2.6 | **Toast & Snackbars** | ✅ Adopted | One toast system, bottom-centre on mobile, bottom-left on desktop, max 2 concurrent, auto-dismiss at 4 s (6 s if the toast contains an action), and **paused on hover/focus**. Used for: achievement unlocked, quality tier auto-adjusted, save code copied, leaf submitted, offline/online transitions, and error recovery. **Accessibility requirement:** the toast container is a permanent `aria-live="polite"` region that exists in the DOM from first paint — creating the live region at the same moment as the message means screen readers announce nothing, which is the single most common toast bug in production. Critical errors use `role="alert"` (assertive) instead. |
| 2.7 | **Infinite Canvas / Dynamic Paging** | ✅ Adopted | Three surfaces genuinely need free 2D pan/zoom: the **Tree orbit view**, the **architecture diagrams** in project panels (a diagram compressed to fit a phone screen is unreadable), and the **world map** in the Village fountain. One shared `<PanZoomSurface>` component: pointer events (mouse/touch/pen unified), pinch-zoom, momentum with friction, min/max zoom clamps, double-tap to fit, and a **"Reset view" control that is always visible** — because the universal failure of pan-zoom UIs is a user who has panned into empty space with no way back. Keyboard: arrows pan, `+`/`-` zoom, `0` resets. |

### The interaction budget

To prevent the accumulation of well-intentioned motion into noise, a hard cap:

> **No more than two animations may run concurrently in the visitor's foveal region.** Enforced by an `AnimationCoordinator` that queues micro-interactions rather than firing them simultaneously. When a memory recovery and an achievement toast collide, the toast waits 4.2 s. The peak moment stays a peak.

## 3 · UI STATES & RESILIENCE

### The component state matrix

Every interactive element in Layer 2 implements this matrix. It is a Storybook requirement — a component without all applicable states does not merit a version.

| State | Visual rule | A11y rule |
|---|---|---|
| **Default** | Base token values | — |
| **Hover** | Background +6% luminance, 120 ms ease | Never the *only* affordance — hover does not exist on touch |
| **Focus-visible** | 2 px outline, 2 px offset, `--tfm-focus` (contrast ≥ 3:1 against both adjacent surfaces) | `:focus-visible`, never `:focus` — a mouse click must not draw a ring, or users disable focus styles entirely |
| **Pressed / Active** | 2 px translate-Y, background −4% | Fires on `pointerdown` for perceived speed |
| **Disabled** | 45% opacity, `cursor: not-allowed` | `aria-disabled="true"` and **kept focusable** — a `disabled` attribute removes the element from the tab order and a keyboard user can never discover why they are blocked. Paired with a `title`/tooltip stating the reason. |
| **Loading** | Spinner replaces the label, **width locked at the label's measured width** | `aria-busy="true"`; the label is retained for screen readers |
| **Error** | 2 px border `--tfm-error`, icon + text (never colour alone) | `aria-invalid`, `aria-describedby` → the message |
| **Success** | Icon + text, 3 s then returns to default | `role="status"` |
| **Empty** | See below | Headline is a real `<h*>`, not a styled `<div>` |
| **Selected** | Filled background, contrast ≥ 4.5:1 | `aria-selected` / `aria-pressed` |

### Decisions

| # | Standard | Verdict | Implementation in this project |
|---|---|---|---|
| 3.1 | **Default / Hover / Pressed / Active / Disabled** | ✅ Adopted | The matrix above, encoded as design tokens and enforced in Storybook. |
| 3.2 | **Empty States / Zero State** | ✅ Adopted | Eight authored empty states, each with an illustration, a headline, one sentence, and **exactly one action**. The important ones: **Codex with 0 memories recovered** — *"Nothing recovered yet. The world holds a hundred memories; I can open them all now if you would rather not walk."* → **[Reveal everything]**. This is the Impatience Detector's destination and it must never read as a failure. **Tree with 0 leaves** — *"No one has been here yet. You would be the first."* → **[Leave a memory]** (this is the best possible first-visitor experience, and it will only ever be seen once, which is exactly why it is worth authoring). **Search with no results**, **diary empty**, **offline with no cache**, **achievements empty**, **filtered projects empty**, **rejected leaf**. |
| 3.3 | **Error / Success States** | ✅ Adopted | Never colour alone (fails colourblind users, ~8% of men). Always icon + colour + text. Error copy states **what happened, why, and the next action** — never a status code. The world's errors are in-fiction: a failed asset load is *"That memory is not settling. Give me a moment."* while the retry runs silently behind it. |
| 3.4 | **Offline First / Local Caching** | ✅ Adopted — **and it is a headline feature** | A portfolio that works on a plane is a genuine differentiator. A Workbox service worker with four strategies: **app shell** (precache, cache-first), **Codex routes** (stale-while-revalidate), **3D assets** (cache-first with an LRU cap of 120 MB and explicit `.ktx2`/`.glb`/`.opus` handling), and **API** (network-first with a 3 s timeout → cached fallback). The save is `localStorage`, so **progress never depends on a network**. Offline capability: the entire Codex ✅, the whole world once visited ✅, Guardian AI ❌ (falls back to the scripted tree, and says so in character), leaf submission ⚠️ (queued via Background Sync and planted when connectivity returns). A subtle persistent indicator appears when offline; it is informational, never a modal. |
| 3.5 | **Graceful Error Handling / Self-Healing UI** | ✅ Adopted | Error boundaries at four granularities so a failure never takes the page: **per Codex panel** (a broken project card shows a retry, the page survives), **per world area** (a chunk that fails to load returns the player to the Village with an in-fiction line rather than a white screen), **per system** (Guardian, audio, and physics each fail independently — audio failing must never stop the game), and **root** (a designed crash page offering the Codex, the save code for export, and a reload). **The one that matters most and is almost always forgotten: `webglcontextlost`.** Browsers drop the GL context on tab-switch, GPU pressure, or driver hiccups, and the default is a permanently frozen black canvas. This project calls `event.preventDefault()`, shows *"The world is catching its breath…"*, and rebuilds the scene from the save on `webglcontextrestored`. Without this handler, a percentage of sessions end in a dead canvas that the user reads as "this site is broken." |
| 3.6 | **Graceful Degradation** | ✅ Adopted | A degradation ladder that already runs the length of this project: WebGPU → WebGL2 → Codex; Ultra → Minimal quality tiers with a live adapter; Guardian AI → 120-response scripted tree; VO → subtitles; audio → visual-only puzzle feedback (every audio puzzle is solvable mute by design); database down → Tree renders from edge cache, read-only; a failed puzzle asset → automatic skip with rewards granted. **The invariant: every degradation preserves the portfolio.** The floor is never a broken page; the floor is always `/codex`. |
| 3.7 | **State Preservation / Restoration** | ✅ Adopted | Restored on return: area, exact player position and camera orientation, per-puzzle mid-solve state, LUMA stage and last 8 conversation turns, weather (for the session), settings, and scroll position on Codex routes. Save triggers: debounced 2 s after any change, plus **`visibilitychange` → `hidden`** and **`pagehide`** — `beforeunload` is unreliable on mobile Safari and must not be the only hook, which is how "I lost my progress when I switched apps" bugs happen. `bfcache` compatibility is preserved (no `unload` listeners anywhere). Returning after 7+ days shows the "what's new" card ([GDD 5.9](GDD.md#59--the-living-world)). |
| 3.8 | **Edge-Case Design Patterns** | ✅ Adopted | An explicit register, tested with a Storybook "torture" story per component: **long text** — leaf names capped at 24 chars server-side *and* `text-overflow: ellipsis` client-side (never rely on one); project titles wrap to 2 lines then truncate. **RTL** — Arabic is a first-class locale, not a mirror; `dir="rtl"` with logical properties (`margin-inline-start`, never `margin-left`) throughout, and **the 3D world's UI overlays flip while the world geometry does not** (mirroring a 3D scene would break every authored composition and puzzle). **Zero and huge numbers** — `0 / 100` and `9,999+ leaves` both tested. **Slow network** — throttled 3G in CI. **Save-Data / 2G** — the world offers the Codex first. **Battery below 20%** — mobile drops to the Low tier and offers the Codex. **Reduced memory** (`navigator.deviceMemory ≤ 4`) — starts at Medium. **Missing translation** — falls back to English with a `data-untranslated` marker that fails CI rather than shipping a blank string. **Very long session** (> 2 h) — a memory audit runs and unloads unvisited chunks. |

## 4 · MEDIA OPTIMIZATION

| # | Standard | Verdict | Implementation in this project |
|---|---|---|---|
| 4.1 | **Image Caching** | ✅ Adopted | All images are content-hashed and served `Cache-Control: public, max-age=31536000, immutable`, so a repeat visit re-downloads nothing. The service worker holds a 60 MB LRU image cache. `next/image` generates AVIF → WebP → JPEG with a `<picture>` fallback chain. |
| 4.2 | **Blurhash / LQIP** | ✅ Adopted | Every Codex image ships a **BlurHash** string in its front-matter, generated at build time by `scripts/optimize-assets.ts` and rendered as a canvas placeholder — 28 bytes inline instead of a 2 KB base64 LQIP, and it is decoded before the image request even starts. Applied to: project screenshots, certificate scans, diary images, OG previews. **The 3D equivalent is different and worth stating**, because a BlurHash means nothing to a GPU: textures load progressively as **KTX2 mipmap chains**, so a surface appears at 1/16 resolution within the first frames and refines upward. Same perceptual goal — never show an empty rectangle — different mechanism. |
| 4.3 | **Progressive Image Loading** | ✅ Adopted | BlurHash → low-res → full, cross-faded over 300 ms. Every image element declares `width`/`height` or `aspect-ratio` so the box is reserved before the pixels arrive ([Zero CLS, 5.13](#5--performance-memory--engine-level)). Videos (the 12-second project loops) use `preload="none"` with a poster frame, and only fetch on user intent — autoplaying ten silent videos in a portfolio is a bandwidth insult. |

## 5 · PERFORMANCE, MEMORY & ENGINE LEVEL

This section is where a 3D portfolio lives or dies. [GDD Part 12](GDD.md#part-12--performance-budgets) sets the numeric budgets; this section sets the *techniques* that meet them.

| # | Standard | Verdict | Implementation in this project |
|---|---|---|---|
| 5.1 | **Debouncing & Throttling** | ✅ Adopted | A named policy per call site, because "add a debounce" without a number is not an engineering decision: save writes debounce 2,000 ms; the Codex search input debounces 250 ms; telemetry batches on a 5,000 ms flush or 20 events; `ResizeObserver` throttles to 100 ms; the quality-tier adapter samples on a 3,000 ms rolling window; scroll-driven prefetch throttles to 200 ms; the Guardian input is debounce-free but **rate-limited and disabled while a request is in flight** (debouncing a send button is the wrong tool — disable it). |
| 5.2 | **Virtualization / Windowing** | ✅ Adopted, in two distinct forms | **Layer 2:** `@tanstack/react-virtual` on the Tree list past 200 items ([1.3](#1--lists-loading--data-fetching)). **Layer 1:** the equivalent is a three-stage culling pipeline — frustum culling (Three.js, automatic, kept enabled by never setting `frustumCulled = false` as a lazy fix for a bounding-box bug), **distance culling** per instance via the LOD system, and **chunk-level culling** where non-adjacent areas are not merely invisible but fully unloaded from GPU memory. Rendering only what is on screen is the same idea in both layers; only the substrate differs. |
| 5.3 | **Memoization / Component Recycling** | ✅ Adopted | **Layer 2:** `React.memo` applied *selectively* — on the leaf card and the memory tile, the two components that render in bulk; blanket memoization elsewhere costs more in comparison than it saves. `useMemo` reserved for genuinely expensive derivations, not for object literals. **Layer 1:** aggressive **object pooling** — pre-allocated pools of `Vector3`, `Quaternion`, `Matrix4`, raycasters, particles, and audio nodes, all reused. This is what delivers the GDD's "0 bytes garbage per frame" budget; allocating a `new THREE.Vector3()` inside `useFrame` at 60 fps produces 3,600 objects per minute and a visible GC stutter every few seconds. |
| 5.4 | **Re-render Optimization** | ✅ Adopted | Already [GDD Architectural Rule 1](GDD.md#the-three-critical-architectural-rules): React never renders per frame. Enforced by three mechanisms rather than discipline alone — Zustand `subscribeWithSelector` with **transient** subscriptions (`store.subscribe(sel, cb)` mutates refs without triggering React), an ESLint rule banning `useState` inside `useFrame` scope, and the **React DevTools Profiler as a CI gate**: a scripted 10-second gameplay capture asserts **zero React commits**. A re-render during gameplay fails the build. |
| 5.5 | **Batching Updates** | ✅ Adopted | React 19 auto-batches. Beyond that: telemetry events batch into a single request; leaf submissions are single but the moderation queue processes in bulk; `InstancedMesh` matrix updates write to the buffer once per frame with a single `needsUpdate` flag rather than per instance; audio parameter changes batch into one `AudioDirector` tick. |
| 5.6 | **Layout Thrashing / Reflow** | ✅ Adopted | **The rule: never read layout inside `useFrame` or a scroll handler.** No `getBoundingClientRect()`, `offsetWidth`, or `scrollHeight` in a per-frame path — those force a synchronous style recalculation and stall the frame. Element sizes come from `ResizeObserver` and are cached. The canvas resizes from a debounced observer, not from `resize` + measure. In the Codex, reads and writes are separated into distinct phases within any batch operation. |
| 5.7 | **Code Splitting / Dynamic Imports** | ✅ Adopted | The split map: title screen (~40 KB, no Three.js at all) · world engine (`next/dynamic`, `ssr: false`) · per-area scene modules · per-puzzle modules (the Terminal's tokenizer never loads for a player who does not reach the Studio) · the arcade minigame · the Codex (separate route bundle, ~20 KB) · admin (never in the public bundle). |
| 5.8 | **Tree Shaking** | ✅ Adopted, with a named hazard | Generic tree-shaking is table stakes; **the specific hazard in this project is Three.js**, which is large and imperfectly shakeable. Three mitigations: import named exports from `three` (never `import * as THREE` in shipped code, only in scratch), prefer `three-stdlib` over `three/examples/jsm` for better ESM boundaries, and run `@next/bundle-analyzer` on every PR touching `src/world/` with the report posted as a PR comment. `sideEffects: false` is set where accurate. The 400 KB engine budget is not achievable without this. |
| 5.9 | **Payload Reduction** | ✅ Adopted | API responses return only the fields the caller needs (the leaf list omits `ip_hash`, `delete_token`, and `mod_reason` — a `SELECT *` here would leak moderation data to the public). Brotli on all text. The Guardian **streams**, so perceived payload is one token. The 3D asset pipeline is itself the largest payload reduction in the project: Draco + KTX2 typically cut a raw glTF by 8–12×. |
| 5.10 | **Frame Budgeting & 120 Hz Fluidity** | ⚠️ Scoped — **an honest split** | The 8.33 ms budget for 120 Hz is achievable for **DOM/UI** and is adopted there: the Codex, all overlays, and all micro-interactions run on compositor-only properties and comfortably hit 120 Hz on capable displays. It is **not** adopted as a target for the 3D world, and claiming otherwise would be dishonest. A world with real-time shadows, post-processing, and 40k instances cannot hold 8.33 ms on the mid-tier hardware this portfolio must serve. **The decision: the world locks to 60 fps** (16.6 ms) via a fixed-timestep logic loop at 60 Hz decoupled from render, with interpolation — so the simulation is deterministic and stable regardless of display refresh. A **120 Hz mode exists on the Ultra tier only**, opt-in from settings, which drops post-processing to bloom-only and disables SSAO to buy the headroom. A stable 60 beats an oscillating 90 in perceived quality every time, and this is the trade this project makes deliberately. |
| 5.11 | **Off-Main-Thread Execution** | 🔄 Web equivalent (JSI is React Native) | JSI does not exist on the web; **Web Workers, `OffscreenCanvas`, and WASM** are the equivalents, and five workloads move off the main thread: **(a)** Draco and KTX2 decoding (Three.js worker pools — already worker-based, but the pool size is tuned to `hardwareConcurrency - 2` rather than left at default). **(b)** Save compression/decompression (`lz-string` on a worker; compressing a 600-char save on the main thread during a cinematic is a visible hitch). **(c)** The seeded world-event generator, which runs a few thousand hash operations at session start. **(d)** The arcade minigame on `OffscreenCanvas`, so it cannot stall the world behind it. **(e)** BlurHash decoding. Physics stays on the main thread — Rapier's WASM is fast enough at 40 bodies, and the worker round-trip would add more latency than it removes. |
| 5.12 | **GPU-Accelerated Animations** | ✅ Adopted | **Layer 2:** `transform` and `opacity` exclusively. Animating `width`, `height`, `top`, `left`, `margin`, or `box-shadow` is banned and caught by a Stylelint rule. `will-change` is applied *immediately before* an animation and **removed after** — a permanent `will-change` is a permanent GPU layer, and enough of them exhaust VRAM and slow the very thing they were meant to speed up. **Layer 1:** all world animation is inherently GPU-side — vertex shaders for foliage sway and instance growth, GPU particles, and the single `uRestoration` uniform driving the entire healing system with zero per-frame CPU cost. |
| 5.13 | **Layout Shifts Elimination (Zero CLS)** | ✅ Adopted — **target 0.00, not "< 0.1"** | Every image and video declares `width`/`height` or `aspect-ratio`. The canvas container is sized before the engine loads. Fonts use `size-adjust`, `ascent-override`, and `descent-override` on the local fallback so the swap from fallback to webfont produces **no reflow at all** — a metrics-matched fallback is the difference between a real 0.00 and a "good enough" 0.05. Skeletons match final dimensions ([1.6](#1--lists-loading--data-fetching)). Toasts and sheets are `position: fixed` and displaced in the top layer, never in flow. Ads, banners, and late-injected content: none exist. |
| 5.14 | **Memory Leak Prevention** | ✅ Adopted — **the highest-risk item in this entire charter** | A long WebGL session leaks by default, and a portfolio someone leaves open in a tab is exactly the scenario that exposes it. Six enforced rules: **(a) Dispose on unload** — every chunk unload calls `.dispose()` on every geometry, material, and texture it owns. Three.js does *not* garbage-collect GPU resources; a removed mesh whose texture is never disposed holds VRAM until the context dies, and this single omission is the most common Three.js memory bug in production. A `DisposalRegistry` tracks every allocation by chunk and asserts a clean sheet after unload. **(b)** Every `addEventListener`, `IntersectionObserver`, `ResizeObserver`, `setInterval`, and `requestAnimationFrame` has a matching teardown in the same file, verified by an ESLint rule. **(c)** Every `fetch` takes an `AbortSignal` and is cancelled on unmount — a resolved fetch writing into an unmounted component's closure keeps the whole tree alive. **(d)** Howler sounds are `unload()`ed on area change. **(e)** Zustand subscriptions return their unsubscribe and it is called. **(f) A CI leak test**: an automated 15-minute session that visits all 19 areas twice and asserts that `performance.memory.usedJSHeapSize` and the WebGL renderer's `info.memory` return to within 10% of the post-first-area baseline. It fails the build if they do not. |

| 6.7 | **Peak-End Rule** | ✅ Adopted — **and it drives budget allocation** | Memory of an experience is dominated by its most intense moment and its ending, not its average. So: **the peaks** (the gate opening, the Temple revelation, each LUMA stage transition, the ending cinematic) receive **disproportionate polish budget** — bespoke audio, hand-authored camera splines, no reused assets. **The ends** are treated as plural, because different visitors end at different places, and *every* exit must land well: the ending cinematic + Tree for the completionist; **the contact links for the 90-second recruiter** (whose "end" is the Codex contact section, which is therefore polished as carefully as the finale); the "what's new" card for the returner; and the designed 404 for whoever wanders off. A visitor who leaves in the middle still leaves at an end — theirs. |
| 6.8 | **Dopamine Loops & Progressive Disclosure** | ✅ Adopted, ⚠️ with an ethical boundary | The loop is honest: explore → discover → recover → the world *visibly* heals → the Guardian warms → repeat. Progressive disclosure: settings collapse into groups; project panels reveal Run → Code → Architecture on demand; LUMA's personality unfolds across five stages; Codex entries unlock as recovered. **The boundary, stated explicitly: no dark patterns.** No streaks, no daily-login pressure, no artificial scarcity, no "you're 90% done!" nagging, no manipulation of the exit. The weekly challenge is an invitation with no penalty for ignoring it. A portfolio that manipulates its visitors is arguing against its own author's judgement. |
| 6.9 | **Mental Model Alignment** | ✅ Adopted | Standard actions keep standard bindings: `Esc` pauses, `Tab` opens the index, `WASD` moves, browser Back goes back (the world pushes history entries per area so Back does the expected thing rather than dumping the visitor off the site). Metaphors are physical and self-evident: the fountain's water level *is* progress, the Tree's leaves *are* visitors, gears turn, mirrors reflect, water flows downhill. **The one deliberate novelty is the Cursor Ritual** in the opening — and it is placed in the first 30 seconds, with no failure state and no time pressure, precisely because that is the only moment where a visitor has the patience to learn something genuinely new. Novelty later in the experience is friction; novelty at the threshold is invitation. |

## 7 · DESIGN SYSTEMS & GOVERNANCE

| # | Standard | Verdict | Implementation in this project |
|---|---|---|---|
| 7.1 | **Design System** | ✅ Adopted | A single system named **Ember**, spanning both layers. It is not a generic UI kit — it defines the parchment-and-light language of the Codex, the diegetic overlay language of the world, and the shared tokens that let a memory card look like the same object whether it is rendered in WebGL or in HTML. |
| 7.2 | **UI Components** | ✅ Adopted | ~40 components, all built on **Radix UI primitives** for behaviour (focus management, ARIA, keyboard, portals — solved problems that are expensive to re-solve badly) and styled entirely with tokens. Every component ships with all applicable states from the [§3 matrix](#the-component-state-matrix), a Storybook story per state, an RTL story, a long-content torture story, and an axe-core assertion. |
| 7.3 | **Typography** | ✅ Adopted | Four families with defined roles ([GDD Part 9](GDD.md#typography)). A modular scale at 1.25 ratio, expressed as tokens `--tfm-text-{xs,sm,base,lg,xl,2xl,3xl,4xl}`, with `clamp()` for fluid sizing between breakpoints. Line-height and measure are tokens too, and body measure is capped at **65–75 characters** — the single highest-impact readability decision, and the one most portfolios skip. Arabic gets its own scale, because IBM Plex Sans Arabic at 16 px reads smaller than Inter at 16 px and a shared scale would make the Arabic Codex harder to read than the English one. |
| 7.4 | **Color Palette** | ✅ Adopted | The two anchored palettes from [GDD Part 9](GDD.md#palette), plus system colours (error / warning / success / info) and the six category colours. All are authored in **OKLCH**, not hex, so the restoration cross-fade interpolates perceptually rather than drifting through grey — a hex `lerp` from cool grey to warm gold passes through a desaturated mud that OKLCH avoids. Hex values remain in the GDD as reference outputs. Every foreground/background pair is contrast-tested in CI. |
| 7.5 | **Iconography** | ✅ Adopted | Two sets, deliberately separate: **UI icons** (Lucide, 24 px grid, 1.5 px stroke, used only in the Codex and system UI) and **world glyphs** (a custom 44-glyph set on a 32 px grid, used for sigils, achievement niches, leaf symbols, and the runic script in the Temple). Mixing them would break the fiction. Both ship as SVG sprites; neither is an icon font, because icon fonts fail with custom font-blocking, render as boxes on failure, and are announced as garbage characters by screen readers. |
| 7.6 | **Atomic Design Methodology** | ✅ Adopted, mapped to this project | **Atoms**: tokens, Button, Text, Icon, Glyph, Input, Badge, Spinner. **Molecules**: MemoryCard, LeafCard, SkillRing, ToastItem, PuzzleHint, StatePill. **Organisms**: CodexSection, ProjectPanel, TreeList, GuardianPanel, PauseMenu, SettingsSheet. **Templates**: CodexLayout, WorldOverlayLayout, SheetLayout. **Pages**: the 14 Codex routes and the world shell. The world's 3D entities follow the same hierarchy in a parallel tree (`materials → primitives → props → set pieces → areas`), which is what makes the Forest and the Village share 80% of their asset graph. |
| 7.7 | **Multi-Brand & Multi-Theme Architecture** | ⚠️ Scoped — *reframed* | Multi-brand is meaningless for a single-person portfolio and will not be built. But the **multi-theme machinery is genuinely needed**, for three real themes that already exist in the design: light Codex, dark Codex, and **the restoration axis** — which is a continuous theme parameter, unusual and interesting, where `uRestoration` interpolates the entire visual system rather than switching between two discrete sets. Plus four seasonal overlays and a high-contrast theme. All six ship as token *overrides* against one semantic layer, so the theming architecture is real and the brand abstraction is not built. Should a second brand ever be needed, the layer that would carry it is already there. |
| 7.8 | **Semantic Design Tokens Hierarchy** | ✅ Adopted | Strict three tiers, and the discipline that makes them worth having: **Global** (`--tfm-gold-500: oklch(...)`) — raw values, **never referenced by a component**. **Semantic** (`--tfm-color-surface-raised`, `--tfm-color-text-muted`, `--tfm-space-md`) — the only tier components may consume. **Component** (`--tfm-button-primary-bg: var(--tfm-color-accent)`) — per-component overrides. A Stylelint rule fails any component file referencing a Global token directly. Tokens live in one `tokens.json`, are compiled by **Style Dictionary** into CSS custom properties, a TypeScript module, GLSL constants (so shaders and CSS share the same palette), and a Figma variables file. |
| 7.9 | **Accessibility & WCAG 2.2** | ⚠️ Scoped — **honestly** | Claiming blanket AAA for a 3D exploration game would be false. The real commitment, stated per surface: **The Codex targets WCAG 2.2 AAA** and can genuinely meet it — 7:1 contrast on body text, 4.5:1 on large text, full keyboard operation, no timing constraints, no motion requirement, reading level and abbreviations addressed, 44×44 targets (AAA 2.5.5), consistent help (2.4.11), and no drag-only interaction (2.5.7). **The world targets WCAG 2.2 AA** plus every AAA criterion it can meet, and cannot meet a handful by nature — 1.4.6 contrast against a dynamic 3D background and 2.4.9 link-purpose-from-link-text-alone do not have honest answers inside a rendered scene. **The resolution is architectural, not cosmetic**: the Codex is a complete, AAA-conformant equivalent of 100% of the world's content, reachable in one input from anywhere. That is a legitimate conforming alternate version under WCAG, and it is *why the two-layer design is an accessibility decision as much as a business one*. A published accessibility statement at `/accessibility` documents exactly this, including what is not met and why — a specific honest statement is worth more than a vague compliant one. |
| 7.10 | **Design System Governance & Versioning** | ✅ Adopted, sized for the team | Full RFC processes are overhead for one developer, so governance is reduced to what actually prevents drift: every component carries a **maturity level** (`experimental` / `stable` / `deprecated`) in its Storybook metadata; the token file is **semver-versioned** with a changelog; a deprecation requires a replacement to exist and a codemod or a documented migration; visual regression tests (Chromatic or Playwright screenshots) catch unintended changes; and a **quarterly audit** flags components with only one usage (candidates for inlining) and duplicated patterns (candidates for extraction). |

| 9.10 | **Deep Linking / Universal Links** | ✅ Adopted, and used for more than navigation | Every Codex route is a real, shareable, crawlable URL. Beyond that, three deep-link families with real jobs: **(a) World deep links** — `/world?area=temple` (an area jump for returning visitors), `/world?reveal=all` (all memories unlocked — **this is the link the developer puts on a job application**, so the recipient lands in the world with nothing locked), `/world?seed=…` (reproduces an exact weather/event configuration, which is how a bug report becomes reproducible). **(b) Share links** — `/share/[hash]` for the memory card. **(c) Content links** — `/codex/projects/[slug]` with anchor support, so a specific architecture decision can be linked in a conversation. All are server-rendered with correct OG metadata, so every one of them unfurls properly when pasted into Slack, LinkedIn, or a message. |

## APPENDIX A — THE REJECTION REGISTER

Every item that was **not** adopted, with the reason. A charter that adopts everything has made no decisions.

| Item | Reason for rejection |
|---|---|
| **FlashList** (the library) | React Native only; cannot run in a browser. Its *technique* is adopted twice — `@tanstack/react-virtual` in the DOM and `InstancedMesh` on the GPU. |

Replaced by anonymous 3D position heatmaps and scroll-depth events, which answer the same questions better for this specific product. |

Replaced by a truthful split: AAA on the Codex, AA+ in the world, and the Codex as a conforming alternate version for 100% of content. |
| **120 Hz for the 3D world as a default target** | Not achievable at 8.33 ms with shadows, post-processing, and 40k instances on the mid-tier hardware this must serve. A locked 60 fps beats an oscillating 90. A 120 Hz opt-in exists on the Ultra tier with reduced post-FX. |

| **Icon fonts** | Fail as boxes when font loading is blocked and are announced as garbage by screen readers. SVG sprites instead. |

| **Persistent `will-change`** | Creates permanent GPU layers; enough of them exhaust VRAM and slow down what they were added to speed up. Applied immediately before an animation and removed after. |
| **Streaks, daily-login pressure, artificial scarcity** | Dark patterns. A portfolio that manipulates its visitors argues against its author's judgement. |
